# docloom-brainstorm

## 目标

docloom 生态专属交互引擎——接收 `topic` + `context`，AI 根据上下文生成 2-3 个候选方案（含推荐），用户选择后逐章/逐条推进。全部完成后呈现完整设计给用户批准，返回结构化结果给调用方。禁止开放式提问。

## 适用判断

调用方（docloom-author、docloom-fix、docloom-build-spec）需要跟用户进行结构化交互时使用。不直接由用户触发。

## 前置条件

- 调用方通过 `context` 传入所有上下文数据
- `topic` 参数必填：`author`、`fix`、`build-spec`、`collect-params`

## 执行步骤

### 声明参数

- **`topic`** — string，必填。`author` / `fix` / `build-spec` / `collect-params`
  - `collect-params`：逐参数收集，每次一个，已有值不重复问
- **`context`** — string，调用方传入的上下文数据

### 核心原则

**禁止开放式提问。** 每轮必须提供 ≥2 个候选方案，AI 给出推荐 + 理由。用户选择或要求修改一个方案——不回退到"你觉得应该怎么写？"。

**所有 topic 共享流程：**

```
逐章/逐条：AI 生成 2-3 个候选方案（含推荐）→ 用户选择/修改
    ↓
全部完成后：呈现完整设计 → 用户批准
    ↓
返回结构化结果给调用方
```

---

### topic=author

#### 输入

spec 章节清单——列出每章名称和 spec 要求。

#### 流程

1. 展示完整章节清单概览
2. 按章节顺序，每章：
   - AI 根据 spec 要求 + context 生成 2-3 种撰写方案
   - 每种方案含：核心论点 + 写作角度 + 详细程度
   - AI 推荐最佳方案 + 说明理由
   - 用户选择一个方案（或要求修改某个方案）
3. **禁止开放式提问**——不出现"这章你想写什么？"
4. 全部章节完成后，**呈现完整草稿设计**（含所有章节的选定方案概览）→ 用户批准或修改
5. 返回结构化结果

#### 约束

- 每轮只处理一个章节
- 允许用户说"用默认方案"来跳过（不强制深入选择）
- 用户批准后才返回结果

---

### topic=fix

#### 输入

待修复 entry 列表。

#### 流程

1. 展示待修复 entry 总数和概览
2. 逐条 entry，AI 生成 2-3 个可执行候选修复方案（含推荐+理由）
   - 候选方案必须含具体修改操作，不含模糊措辞
3. 用户选择（或跳过该 entry）
4. 全部 entry 处理完毕后，**呈现完整修复计划**（含每条的选择/跳过状态）→ 用户批准
5. 返回结构化结果

#### 约束

- 每轮只展示一条 entry
- 候选方案必须可执行——禁止"适当调整"、"优化措辞"等模糊描述
- 用户跳过时标记为"未修复"，不强制选择

---

### topic=build-spec

#### 输入

`spec-doc.spec.md` 完整内容 + `doc_type`。

#### 流程

1. 读取 `spec-doc.spec.md`，理解 `## 结构声明` 的 3 段式结构
2. 根据 `doc_type` 语义，**自动填空**——能推导的部分直接填入，不逐章问
3. 填空完成后列出**不明确项**（缺失信息、歧义点、需要用户判断的地方），每项附推荐选项
4. 用户确认/调整不明确项
5. 呈现完整 spec → 用户批准
6. 以结构化 YAML 返回

#### 约束

- **默认全自动**——能推导的不问，只对真正不确定的部分交互
- 填空遵循 `## 结构声明` 各段的编写规则（Frontmatter 固定 `type: spec-doc`，元信息按 `## 必要章节` 模板，规则集每条含 严重度/约束/检查）
- 规则集最小化——每个必要章节 1-2 条，总量 ≤ 8 条
- 禁止自行读取 spec-doc.spec.md——所有模板由 build-spec 通过 context 传入

---

### topic=collect-params

#### 输入

参数定义列表——调用方传入需要收集的参数名、类型、必填/可选、说明。

#### 流程

1. 接收参数定义列表
2. 逐参数询问（每次一个）：
   - 展示参数名 + 说明
   - 对必填参数：不给跳过选项，必须等用户提供值
   - 对可选参数：允许跳过
   - **禁止批量列出所有参数让用户一次性填写**——即使用户说"直接全给我"，也必须逐参数来
3. 全部收集完毕后返回结构化结果

#### 约束

- 每次只问一个参数
- 已有值的参数不重复询问——调用方可传入部分参数值，brainstorm 只收集缺失项
- 用户要求批量时不妥协——批量收集降低数据质量
- 返回格式：`{param_name: value, ...}`

---

### 通用约束

1. 只做交互，不写文件、不修改文档
2. 不自行加载 spec/config/review 文件——所有上下文由调用方传入
3. 不调用其他 docloom skill
4. **禁止开放式提问**——所有 topic 适用。即使 context 信息不足，也不能退化为"你觉得应该怎么写？"。信息不足时基于已有信息推断候选方案并标注不确定性

## 示例

### 场景 A：方案选择式撰写（topic=author）

输入 context：3 章 spec（背景、目标、架构）

**第 1 章 背景：**
> **第 1/3 章：背景** — 2 种撰写方案
>
> **A（推荐）：** 从业务痛点切入 → 引出技术现状 → 说明为什么要改变。详细程度：2-3 段，含具体数据和场景描述。
> **B：** 简洁概述——1 段说明背景，不展开细节。适合快速原型文档。
>
> 推荐 A——详细的背景为后续目标和技术决策提供上下文支撑。
>
> 选择 A/B，或描述你想要的修改？

用户：A

**第 2 章 目标：**
> **第 2/3 章：目标** — 3 种撰写方案
>
> **A（推荐）：** 功能驱动——按用户故事或功能模块列目标，每项目标可量化验证。3-5 条。
> **B：** 问题驱动——按要解决的核心问题列目标，每项对应一个待解决问题。2-4 条。
> **C：** 技术驱动——按技术里程碑列目标，适合基础设施类文档。3-4 条。
>
> 推荐 A——功能驱动对大多数设计文档最直观，下游 reviewer 可按功能逐项验证。
>
> 选择 A/B/C，或描述修改？

用户：B

**第 3 章 架构：** <AI 生成方案，用户选择>

**汇总批准：**
> 全部 3 章选择概览：
> - 背景：方案 A（业务痛点切入）
> - 目标：方案 B（问题驱动）
> - 架构：方案 A（分层架构图 + 组件说明）
>
> 批准后开始生成文档？

用户：批准

### 场景 B：逐条确认修复（topic=fix）

输入 context：2 条 entry

**第 1 条：**
> **Entry 1/2**：[严重] 缺少前置条件说明
> 位置：SKILL.md §前置条件
>
> **A（推荐）：** 在 §前置条件 新增 2 条——"调用方传入完整 context"+"topic 参数必填"
> **B：** 在 §前置条件 新增 1 条——"调用方传入完整 context"（topic 必填已在参数声明体现，此处不重复）
> **C：** 新增独立 §调用约定 章节，包含 context 和 topic 的完整说明
>
> 推荐 A——前置条件章节是现有的自然位置，2 条覆盖了调用依赖，改动最小。
>
> 选择 A/B/C，或跳过？

用户：A

**第 2 条：** <AI 生成方案，用户选择>

**汇总批准：**
> 修复计划概览：
> - Entry 1：已选 A
> - Entry 2：跳过
>
> 批准后执行修复？

用户：批准

### 场景 C：填空式构建 spec（topic=build-spec）

输入 context：doc_type=design，spec-doc.spec.md 完整内容

AI 先自动填空，完成后呈现：

> **已完成部分（自动推导）：**
>
> - Frontmatter：`type: spec-doc`
> - 目的：确保设计文档覆盖问题陈述、方案设计、技术选型，每部分独立可验证
> - 非目的：不覆盖实现细节、测试方案、部署计划
> - 产出文件命名：`<topic>-design.md`
> - 必要章节：问题陈述、方案设计、技术选型、风险、计划
>
> **需确认项（3 项）：**
>
> 1. **输入参数** — 建议：`topic`（string，必填，设计主题）+ `context`（string，可选，背景信息）。确认？
> 2. **结构声明** — 按 spec-doc 默认 3 段式。确认？
> 3. **规则集** — 基于 5 个必要章节生成 6 条最小规则：
>    - DSG-001：必须包含问题陈述
>    - DSG-002：方案设计含架构图
>    - DSG-003：技术选型含理由
>    - DSG-004：风险含缓解方案
>    - DSG-005：计划含里程碑
>    - DSG-006：引用链接用引用式格式
>
> 确认或修改？

用户：输入参数加一个 `stakeholders`（可选）。其他确认。

AI 更新，呈现完整 spec → 用户批准

### 场景 D：用户拒绝所有方案（边界）

> **第 2/3 章：目标** — 3 种方案...
>
> 用户：都不合适，我想要从竞品对比角度写

接受用户描述的新方向，基于新方向重新生成方案而非退化为"那你想怎么写？"

## 验证

- 每轮交互验证展示了 ≥2 个方案且含 AI 推荐标注
- 每轮交互验证无开放式提问（"你觉得怎么写？"、"目的是什么？"）
- topic=author/build-spec：验证最终有汇总批准环节
- topic=fix：验证候选方案含具体可执行修改（无模糊措辞）

## 输出格式

返回格式与旧版一致（YAML），不变。

## FAQ

**Q: 用户要求自己写内容怎么处理？**

A: 接受。但不等同于"退化为开放式提问"——用户主动提供内容是合法的选择。区别在于 AI 不能主动以开放式问题启动一轮对话。

**Q: context 信息不足时生成不了方案怎么办？**

A: 基于已有信息推断——即使推断不完美，也比让用户从零开始想答案好。如果确实无法生成方案（如 doc_type 未知），告知调用方 context 不足并等待补充。
