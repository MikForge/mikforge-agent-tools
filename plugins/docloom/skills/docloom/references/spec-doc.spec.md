# 产物 Spec 规范

定义产物 spec 的标准结构和规则格式。所有产物 spec 文件（如 plan.spec.md、design.spec.md）必须遵守本文档。

---

## 目的

确保所有产物 spec 文件在顶层结构、规则格式、章节命名上保持一致，下游工具（author、reviewer、fix）可稳定解析。

## 非目的

不定义各文档类型的专属章节内容或业务规则。

## 输入参数声明

- 无外部输入参数 — 本规范定义的是产物 spec 文件的内部格式约束。

## 产出文件命名

产物 spec 名称 `<doc_type>.spec.md`。

## 结构声明

产物 spec 文件采用 3 段式结构：

- **段1：Frontmatter** — YAML 头部，`type` 固定为单值字符串 `spec-doc`，分隔线后紧跟正文无空行
- **段2：元信息** — 6 个 `##` 级章节（目的、非目的、输入参数声明、产出文件命名、结构声明、必要章节），彼此同级排列；输入参数逐行单行格式，禁止嵌套列表
- **段3：规则集** — `---` 分隔线后，`### XXX-slug` 规则按必要章节分组排列，每条规则自包含完整 severity/约束/检查/正反例。**禁止通过 reference link 引用外部 spec 文件——agent 对二级引用敏感，规则内容必须内联。**

## 必要章节

产物 spec 文件必须包含以下 6 个 `##` 级章节（彼此同级）：

- **目的** — 该文档类型要确保什么
- **非目的** — 该文档类型不覆盖什么
- **输入参数声明** — 输入参数逐行格式（`- **`name`** — type，必填/可选。说明。`），无外部输入参数时写 `- 无外部输入参数`
- **产出文件命名** — 产出文件命名规则
- **结构声明** — 产物 spec 的 3 段式结构定义，含每段编写规则的子章节
- **必要章节** — 该类型文档必须包含的章节列表

---

### SDC-frontmatter-format：Frontmatter 格式

- **严重度：** 严重
- **约束：** 产物 spec 文件头部必须包含 YAML frontmatter，`type` 固定为单值字符串 `spec-doc`。`---` 分隔线后紧跟正文第一行，中间无空行。反例——`type` 为数组而非单值字符串；分隔线后有空行。
- **检查：** `type` 为单值字符串 `spec-doc`（严重）；分隔线后无空行（重要）

> **正例：**
>
> ```yaml
> ---
> type: spec-doc
> ---
> # 标题
> ```
>
> **反例：**
>
> ```yaml
> ---
> type: [spec-doc, design]
> ---
>
> # 标题
> ```
>
> 违规说明：`type` 为数组而非单值；分隔线后有空行。

### SDC-meta-sections-complete：元信息章节完整

- **严重度：** 严重
- **约束：** 6 个 `##` 级章节（目的、非目的、输入参数声明、产出文件命名、结构声明、必要章节）必须全部存在，彼此同级排列，位于 Frontmatter 之后、规则集之前。反例——缺少任一章节导致下游工具解析失败。
- **检查：** 目的章节存在（严重）；非目的章节存在（严重）；输入参数声明章节存在（严重）；产出文件命名章节存在（严重）；结构声明章节存在（严重）；必要章节章节存在（严重）

### SDC-input-params-format：输入参数声明格式

- **严重度：** 重要
- **约束：** 每个参数独立一行：`- **`name`** — type，必填/可选，默认：值。说明。`。无默认值时省略"默认："段。无外部输入参数时写 `- 无外部输入参数`。禁止纯自然语言段落式罗列参数或将单个参数拆成多层嵌套列表。反例——单个参数拆成多层嵌套列表，reviewer 无法精确引用。
- **检查：** 参数逐行格式正确（重要）；无嵌套列表（重要）；无外部输入参数时写 `- 无外部输入参数`（轻微）

> **正例：**
>
> ```markdown
> ## 输入参数声明
>
> - **`type`** — string，必填。文档类型 design。
> - **`context`** — string，可选。用户提供的结构化上下文。
> ```
>
> **反例：**
>
> ```markdown
> ## 参数声明
>
> - `doc_type`
>   - 类型：string
>   - 必填：是
>   - 默认值：—
>   - 说明：文档类型标识，如 `plan`。
> ```
>
> 违规说明：单个参数拆成多层嵌套列表。应采用逐行格式，每个参数一行写完。

### SDC-ruleset-structure：规则集分隔与编号

- **严重度：** 严重
- **约束：** 规则集区域必须用 `---` 分隔线与元信息段分隔。每条规则是独立的 `### XXX-slug：规则标题`（`XXX` 为文档类型前缀，`slug` 为英文 kebab-case 描述性标识符，该文档类型内唯一），按必要章节分组排列，末尾无 `## 审查列表` 章节。反例——缺少 `---` 分隔线导致元信息和规则无法区分；仍用旧式 `#### 规则N` 而非 `### XXX-slug` 格式；slug 使用拼音或中文。
- **检查：** 规则集前有 `---` 分隔线（严重）；规则使用 `### XXX-slug` 格式（严重）；slug 为英文 kebab-case（重要）；slug 在文档内唯一（严重）；末尾无审查列表章节（轻微）

> **正例：**
>
> `design.spec.md` 以 `### DSG-001` ~ `### DSG-022` 结尾。
>
> **反例：**
>
> 缺少 `---` 分隔线，或仍用旧式 `#### 规则N` 而非 `### XXX-slug` 格式，或末尾多出 `## 审查列表` 章节；slug 使用拼音或中文。
>
> 违规说明：产物 spec 结构不符合编号规则格式，reviewer 无法按统一编号引用规则。

### SDC-rule-fields-complete：规则字段完整

- **严重度：** 严重
- **约束：** 每条规则正文必须包含三个必填字段：`**严重度：**`（严重/重要/轻微）、`**约束：**`（一句浓缩约束描述）、`**检查：**`（审查时逐项核对，可标注严重度）。反例——缺少任一字段导致 reviewer 无法判断违规等级和检查方式。
- **检查：** 严重度字段存在且值为严重/重要/轻微（严重）；约束字段存在且不为空（严重）；检查字段存在且不为空（重要）

> **正例：**
>
> ```markdown
> ### DSG-001：必需结构 — 问题陈述
> - **严重度：** 严重
> - **约束：** 设计文档必须包含问题陈述，一句话说明要解决的技术问题或要达成的技术目标。反例——仅写"登录太慢了需要优化"而无具体技术问题和量化指标。
> - **检查：** 问题陈述清晰：设计要解决什么问题？（严重）
> ```
>
> **反例：**
>
> ```markdown
> #### 规则1：问题陈述必须清晰
>
> **正例：**
> 登录接口 P99 延迟超 3s...
>
> **反例：**
> 登录太慢了
> ```
>
> 违规说明：旧式 `#### 规则N` 标题，缺少 `严重度/约束/检查` 三段式字段，正反例未用 `>` blockquote 包裹。

### SDC-examples-format：正反例格式

- **严重度：** 重要
- **约束：** 若约束有对应示例，以 `> **正例：**` / `> **反例：**` blockquote 附在规则末尾。正例在前，反例在后。blockquote 为可选——无独立正反例的规则可省略。反例——正反例代码块散落而非 `>` blockquote 包裹；正反例顺序颠倒。
- **检查：** 正反例使用 `>` blockquote 格式（重要）；正例在反例之前（轻微）

> **正例：**
>
> ```markdown
> ### DSG-001：必需结构 — 问题陈述
> - **严重度：** 严重
> - **约束：** 设计文档必须包含问题陈述...
> - **检查：** 问题陈述清晰（严重）
>
> > **正例：**
> >
> > 用户登录接口在高并发场景下响应时间超过 3s，需要重新设计会话管理方案。
> >
> > **反例：**
> >
> > 登录太慢了，需要优化一下。
> ```
>
> **反例：**
>
> ```markdown
> #### 规则1：问题陈述必须清晰
>
> **正例：**
>
> ## 问题陈述
> 登录接口 P99 延迟超 3s...
>
> **反例：**
>
> 登录太慢了
>
> 违规说明：登录太慢缺少技术指标。
> ```
>
> 违规说明：旧式 `#### 规则N` 标题与正反例代码块散落。应采用 `### XXX-slug：标题` 格式 + `严重度/约束/检查` 三段式 + `>` blockquote 正反例。

### SDC-reference-links：引用式链接

- **严重度：** 严重
- **约束：** 全文统一使用 `[显示文字][引用ID]` 引用式链接，所有路径定义集中在文末。禁止行内链接、裸 URL、绝对路径、反引号包裹路径、路径定义散落正文各处。文件引用必须使用相对路径。
- **检查：** 是否存在行内链接？（严重）是否存在裸 URL？（严重）是否存在绝对路径？（严重）路径定义是否集中在文末？（重要）

> **正例：**
>
> 启动时加载 [config.yaml][docloom-config]，验证配置存在。
>
> [docloom-config]: ../docloom/config.yaml
>
> **反例：**
>
> 启动时加载 [config.yaml](https://github.com/xxx/blob/main/config.yaml)。
>
> 问题：行内链接、绝对路径、路径定义未集中在文末。

### SDC-banned-phrasing：禁止措辞

- **严重度：** 严重
- **约束：** 禁止使用以下措辞：占位符 TBD / TODO / "后续补充"等——必须改写为可验证、可执行的具体描述；模糊描述"适当处理" / "按需优化" / "灵活配置"等——必须改写为具体可验证的描述；形容词替代指标"高性能" / "高可用" / "易于扩展"等——必须给出量化标准或判断条件；隐含上下文依赖"类似上一任务" / "同上"等——每条规则必须自包含。
- **检查：** 全文是否含 TBD/TODO/占位符？（严重）是否含模糊描述措辞？（重要）是否用形容词替代量化指标？（重要）是否存在隐含上下文依赖？（轻微）

> **正例：**
>
> 输出格式必须包含 6 个部分：背景、目标、约束、执行规则、验收标准、示例。
>
> **反例：**
>
> 输出时应适当优化格式，尽量简洁。
>
> 问题："适当"、"尽量"为模糊措辞，缺少可判定的具体标准。
